## 1순위 - 리텐션 루프 완성 (v1.0~1.1)

### 1-1. 리포트 공유 카드
왜: 릴스 15개 전략(W4)과 직결 - 유저가 스스로 바이럴 소재를 만들게 됨. 숫자만 공유라 프라이버시 원칙 유지.

**실행 프롬프트:**
```
리포트 공유 카드를 구현해줘.

1. 리포트 화면(app/report.tsx) 하단에 "결과 공유하기" 버튼 추가 - 주요 CTA 아님(보조 위계, 테두리 버튼)
2. 탭하면 공유용 카드 1장을 이미지로 렌더해 OS 공유 시트로 내보내기:
   - 포함: 제품명, 추적 기간(시작→판정 날짜), 판정 결과(개선/변화 없음/악화 + 정수 델타), 구조 지표 3종의 기준선→현재
   - 절대 미포함: 사진, 유저 식별자, evidence 원문(모델 텍스트)
   - 하단에 앱 이름 + "같은 조건으로 재면, 변화가 숫자로 보입니다" 카피
3. 렌더 방식: react-native-view-shot으로 오프스크린 View 캡처 (Expo Go 호환 여부 먼저 확인하고 보고 - 안 되면 dev build 전제 명시)
4. 디자인: UI 원칙 준수 - 화이트 베이스, 숫자 히어로, 민트 1색, 이모지 금지. 카드 비율 4:5 (인스타 피드 기준)
5. 공유 실패(권한/취소)는 조용히 복귀 - 에러 화면 금지
6. 캡처 임시 파일은 공유 완료 후 삭제 (이미지 수명 원칙 준수)

검증: tsc --noEmit + 실기기에서 공유 시트까지 열리는지 확인 절차 안내.
공유 카드에 사진·evidence가 안 들어가는 건 코드 리뷰로 명시 확인해줘.
```

### 1-2. 주간 요약 알림 (주 1회)
왜: "매일 알림 금지" 원칙 안의 최대 허용선. 측정 습관 리마인드를 요약 가치로 포장.

**실행 프롬프트:**
```
주간 요약 로컬 알림을 구현해줘. 매일 알림 금지 원칙은 유지 - 주 1회 1건이 상한.

1. 매주 일요일 저녁 8시(로컬 시간) 반복 트리거 1건: expo-notifications WEEKLY 트리거 사용
2. 문구는 정적 콘텐츠 한계를 고려해 일반형: "이번 주 피부 기록을 확인해보세요 - 숫자는 쌓일수록 정확해져요"
   (로컬 알림은 예약 시점 텍스트 고정이라 실측치 삽입 불가 - 동적 수치 넣으려면 방식 먼저 보고하고 멈춰)
3. 예약 시점: 첫 스캔 완료 시 1회 등록. 이미 등록돼 있으면 중복 예약 금지 (기존 알림 식별은 data 태그 패턴 재사용 - lib/notifications.ts 참고)
4. 알림 권한 거부 상태면 조용히 스킵 (등록 흐름 막지 않기 - 기존 원칙)
5. 설정 화면에 "주간 요약 알림" on/off 행 추가 (기본 on). off 시 취소, on 시 재예약
6. 기록 전체 삭제 시 이 알림도 함께 취소되는지 확인 (cancelAllNotifications 경로)

검증: tsc + 알림 예약 목록을 콘솔로 확인하는 dev 절차 안내.
제품별 알림(리포트 도착·D-7)과 태그가 섞이지 않는지 확인해줘.
```

### 1-3. 측정 스트릭 배지
왜: 판정 정확도(표본 수)와 직결되는 행동을 보상. 서버 변경 없이 클라이언트 계산만.

**실행 프롬프트:**
```
오늘 탭에 측정 스트릭(연속 측정 일수) 표시를 추가해줘.

1. 계산: useScans의 최근 스캔들에서 KST 날짜 기준 연속 일수 산출 - 단 현재 useScans는 10개 제한이라
   스트릭 계산에 부족함. 스트릭용 경량 쿼리(created_at만 select, 최근 60일, limit 60)를 별도 훅으로
2. 날짜 경계는 서버 캡과 동일하게 KST 고정 (클라이언트 시계 이슈는 표기 수준이라 허용 - audit-w3.md 축4 참고)
3. 표기: 오늘 탭 ScoreHeader 근처에 "3일 연속 측정" 칩 1개. 2일 이상일 때만 노출 (1일은 노이즈)
4. 오늘 미측정 상태면 "어제까지 n일 연속 - 오늘 재면 이어져요"로 전환 (문구 주어는 유저 상황 - CLAUDE.md 언어 원칙)
5. 파스텔·이모지·불꽃 아이콘 금지 - 숫자 중심, 민트 칩
6. 스트릭 끊김에 대한 부정 피드백(리셋 경고 등) 금지 - 보상만, 압박 없음

검증: 스트릭 계산 함수는 순수 함수로 분리해 노드 테스트 (연속/공백/KST 자정 경계/오늘 포함·미포함 케이스).
```

## 2순위 - 판정 신뢰도 강화 (v1.1)

### 2-1. 리포트 신뢰도 등급
왜: verdict jsonb에 baseline_scan_count/current_scan_count가 이미 저장돼 있음 - 표시만 추가하는 저비용 고신뢰 작업.

**실행 프롬프트:**
```
리포트에 신뢰도 등급 표시를 추가해줘. 판정 로직(computeVerdict)은 절대 수정 금지 - 표시 레이어만.

1. 등급 산정(표시용 순수 함수, lib/verdict/에 별도 파일):
   - 높음: 기준선 3개 이상 AND 비교군 3개 이상
   - 중간: 양쪽 각 2개 이상
   - 낮음: 그 외 (기준선이 first_scan_after_start면 자동으로 한 단계 강등)
2. VerdictReportView 상단에 "신뢰도 높음/중간/낮음" 칩 - 기존 confidenceLabels 스타일 재사용
3. 낮음일 때만 보조 문구: "측정이 많을수록 리포트가 정확해져요" (다음 사이클 유도 - 압박 아님)
4. 기존 저장된 verdict에도 소급 적용됨 (scan_count 필드가 이미 있으므로 마이그레이션 불요 - 확인 후 보고)
5. ProductCard의 done 요약에는 넣지 말 것 - 리포트 화면 전용

검증: 등급 함수 노드 테스트 (경계값 2/3, first_scan 강등, held 색지표 무관 확인) + tsc.
```

### 2-2. 동시 추적 경고
왜: 제품 2개가 기간이 겹치면 효과 분리 불가 - 판정 결과의 해석 오류를 등록 시점에 예방.

**실행 프롬프트:**
```
제품 등록 시 동시 추적 경고를 추가해줘. 등록 차단이 아니라 안내만 - computeVerdict·등록 흐름 변경 금지.

1. RegisterModal 제출 전, 미완결(verdict null) 제품이 1개 이상 있으면 모달 내 경고 문구 노출:
   "『기존제품명』을 아직 추적 중이에요. 동시에 쓰면 어느 쪽 효과인지 구분이 어려워요"
2. 그래도 등록 가능 (강제 아님) - 버튼 문구는 그대로
3. "4주 더 추적"(같은 제품 연장)은 경고 대상 제외 - 같은 이름이면 스킵
4. 경고 판정에 필요한 products는 호출부(today/verdict/report)가 이미 들고 있음 - RegisterModal에 prop으로 전달, 모달 내 추가 쿼리 금지

검증: tsc + 케이스 확인(미완결 0개/1개/같은 이름 연장) 절차 안내.
```

### 2-3. 시간대 태그 (아침/저녁)
왜: 유수분·붉은기는 시간대 영향이 큼 - 추이 노이즈를 설명하는 최소 장치. 피부 타입 분류(스코프 밖)와 무관.

**실행 프롬프트:**
```
스캔에 시간대 태그를 추가해줘. 서버 스키마 변경이 필요하니 마이그레이션부터 보고하고 진행해.

1. scans에 daypart text 컬럼 추가 (마이그레이션, 기존 행은 null 허용): 'morning'(05-11시)/'day'(11-17시)/'evening'(17-24시)/'night'(00-05시), KST 기준 서버에서 산출
2. 산출 위치: analyze-skin edge function insert 시점 (클라이언트 시계 불신 원칙 유지)
3. 표시: 히스토리 리스트 항목에 작은 회색 텍스트로 병기 ("아침" 등). 점수 화면에는 미표시
4. 추이 그래프(TrendChart)에 시간대 필터 칩 추가 - Pro 전용 유지, 전체/아침/저녁 3개만 (day/night는 표본 적으니 전체에 포함)
5. 판정(computeVerdict)에는 반영하지 말 것 - 표시·필터 전용. 판정 로직 변경은 확정 설계라 사용자 승인 필요

검증: 마이그레이션 Docker 테스트(기존 패턴), daypart 산출 함수 노드 테스트(KST 경계 05/11/17/24시), tsc.
edge function 배포는 내가 하지 말고 명령만 제시 (--use-api).
```

## 신규 축 - 온보딩·계정·목표 (유기적 연결 퍼널)

설계 의도: **첫 실행 → 설득 온보딩 3장(수집 제로) → 첫 촬영 → (분기: 등록 예열) → 목표 → 리포트**로
한 줄로 이어지는 퍼널. 온보딩의 과제는 프로필 수집이 아니라 "왜 같은 조건 측정인가"의 납득.

⚠️ 주의 (구현 전 결정):
- 로그인(4-2)은 현 스택(익명 auth)의 변경 - CLAUDE.md 스택 항목 수정 필요. 다만 백로그의 "세션 persist 점검(익명 유저 10명 사건)"을 근본 해결하는 길이기도 함 - 익명으로 시작해서 나중에 소셜 연동하는 하이브리드가 마찰 최소.
- 온보딩은 개인정보를 수집하지 않음(로컬 저장만) - 처리방침·데이터 보안 폼 추가 부담 없음.
- 성별·나이대 수집은 여기서 하지 않는다: 분포 비교(또래 대비 위치) 기능을 실제로 만들 때, 그 화면에서
  용도를 보여주며 수집(동의율 최대 시점). 용도는 표시 레이어 전용 - 분석 프롬프트 주입 금지(재현성 보호).

### 4-1. 온보딩 플로우 (3장 - 설득 중심, 수집 제로)

**실행 프롬프트:**
```
첫 실행 온보딩 3장을 구현해줘. 스킵 가능, 완료/스킵 후 재표시 없음. 개인정보 수집 없음 - 응답은 로컬 저장만.

1. 노출 조건: AsyncStorage 플래그 미존재 + 스캔 0개인 첫 실행에만. 완료·스킵 모두 플래그 기록 → 재표시 없음
2. 1장 - "당신의 거울은 매일 거짓말을 합니다": 조명·기분에 따라 달라 보이는 피부 → 그래서 같은 조건
   측정이 필요하다. 텍스트+미니 비주얼 1개(일러스트 금지 원칙 - 숫자/도형 기반)
3. 2장 - 촬영 통제 소개: 타원+화면 플래시 비주얼(FaceGuideOverlay 시각 요소 재사용),
   "같은 순간을 두 번 재면 같은 숫자가 나옵니다" + "사진은 분석 후 즉시 삭제됩니다" 병기
4. 3장 - 선택 질문 1개 "지금 제일 궁금한 건?":
   (a) 내 피부 상태 점수 → 완료 후 촬영 화면으로
   (b) 쓰는 화장품이 효과 있는지 → 완료 후 촬영 화면으로 + 분석 완료 시 SampleReportCard를 먼저 강조
   ⚠️ b에서 등록 모달을 바로 열지 말 것 - 등록은 Pro 기능이라 첫 경험이 페이월이 되는 충돌.
   샘플 리포트(14일 뒤의 그림)로 예열 후 기존 진입점(startVerdict 버튼 펄스)에 맡긴다
5. 응답(a/b)·완료/스킵 여부는 AsyncStorage에만 저장 - 서버 전송 금지, 분기 외 용도 없음을 주석 명시
6. 로컬 퍼널 카운트: 각 장 도달·스킵·a/b 선택을 로컬 카운터로 기록 (dev 메뉴에서 열람 -
   "b가 다수면 판정이 진짜 수요"라는 포지셔닝 검증용. 외부 전송 없음)
7. 스킵 유저 커버: 1~2장의 핵심 한 줄("같은 조건 측정", "사진 즉시 삭제")은 카메라 첫 진입
   1회 오버레이(master-plan UI 항목)에 중복 배치 - 온보딩 스킵이 정보 상실이 되지 않게
8. 문구 전부 strings.ts + 언어 원칙. 화면 3장 초과 금지, 서버 스키마 변경 없음

검증: tsc + 첫 실행/스킵/재실행/a·b 분기 4케이스 확인 절차 안내. 서버 전송이 없음을 코드 리뷰로 명시 확인.
```

### 4-2. 계정 연동 (익명 → 소셜 로그인)

**실행 프롬프트:**
```
계정 연동을 구현해줘. 방향은 "익명으로 시작, 원할 때 연동" - 첫 실행에 로그인 강제 금지
(촬영까지의 마찰 최소화 원칙). 익명 유저 데이터가 연동 후에도 유지되는 게 핵심.

1. 방식: supabase auth linkIdentity (익명 세션에 Google 계정 연결 - 기존 user_id 유지되어
   scans/products/profiles 전부 보존). Apple은 iOS 작업(W3 후반)과 함께
2. 진입점 2곳: ① 설정 화면 상단 "계정" 행 (미연동: "데이터 지키기 - Google로 연동" / 연동됨: 이메일 표시)
   ② 첫 리포트 완료 화면 하단 1회 노출: "이 기록, 기기를 바꿔도 지키려면 계정 연동"
   (가치를 경험한 직후가 연동 동기 최대 시점 - 그 외 위치에 반복 노출 금지)
3. 연동 성공/실패/이미 다른 계정에 연동됨(identity_already_exists) 각각 한국어 문구 분화
4. 로그아웃은 넣지 말 것 - 익명 복귀 시 데이터 접근 상실 문제가 있어 v1은 연동만. 필요해지면 별도 논의
5. expo-auth-session 기반 (Expo Go 동작 여부 먼저 확인 - 안 되면 dev build 전제 보고)
6. 백로그 "세션 persist 점검"이 이 작업으로 해소되는지 확인하고 결과를 CLAUDE.md 백로그 갱신안으로 제안
   (CLAUDE.md 수정은 내 승인 후)

검증: tsc + 연동 전후 user_id 동일성 확인 절차(콘솔 로그) + scans 행 접근 유지 확인 절차 안내.
```

### 4-3. 목표(Goal) 기능 - 리포트와 유기 연결

**실행 프롬프트:**
```
목표 기능을 구현해줘. 온보딩(4-1)의 사용 목적에서 이어지고, 14일 리포트에서 회수되는 구조 -
독립 기능이 아니라 기존 판정 루프에 얹는 레이어다. computeVerdict 수정 금지.

1. 목표 정의: "지표 X를 14일 안에 +5" 형태만 (5점 밴드와 정합 - 임의 목표치 입력 금지).
   지표 기본 제안은 최근 스캔의 우선순위 1가지(PriorityCard와 동일 소스)에서, 변경 가능
   (온보딩 4-1은 수집 제로 설계라 서버 프로필이 없음 - 온보딩 b 선택 여부는 로컬 참고만)
2. 저장: goals 테이블 (user_id, metric_key, target_delta int default 5, started_at, achieved boolean null,
   product_id uuid null - 제품 추적과 연결 시). RLS 본인 행. 활성 목표는 유저당 1개 (단순성 우선)
3. 오늘 탭: ScoreHeader 아래 목표 진행 칩 - "목표: 트러블 +5 · 현재 +3" (최근 스캔 vs 목표 시작 시점 스캔,
   클라이언트 계산). 목표 없으면 미표시
4. 리포트 연결: 리포트 화면에서 활성 목표의 지표가 판정에 포함돼 있으면 결론 문구에 1줄 추가 -
   달성: "목표했던 트러블 +5, 이번 사이클에서 도달했어요" / 미달: "트러블은 +3 - 다음 사이클에서 이어가요"
5. 목표 달성/미달 판정은 리포트 열람 시점에 계산해 goals.achieved 갱신 (별도 알림 금지 - 알림 원칙 유지)
6. 문구 전부 strings.ts + 언어 원칙 (심판 언어 금지 - "달성 실패" 같은 표현 대신 진행형)
7. 다음 사이클 시작(4주 더 추적/새 제품 등록) 시 목표 갱신 제안 시트 - 온보딩→목표→리포트→재목표 루프 완성

검증: 목표 진행 계산 순수 함수 노드 테스트 (달성/미달/지표 held/스캔 0개), 마이그레이션 Docker 테스트, tsc.
```

### 권장 구현 순서
4-1(온보딩) → 4-3(목표) → 4-2(계정 연동). 목표가 온보딩 데이터를 바로 소비해야 퍼널이 살고,
계정 연동은 "지킬 가치가 있는 기록"이 쌓인 뒤가 전환율이 높음.
