# Fable 리뷰 프롬프트 (docs/project-guidelines.md 생성용)

용도: `/model`로 Fable 전환 후, 아래 블록을 그대로 복붙해 `docs/project-guidelines.md`를 생성.
목적: 프로젝트의 하자(결함·사각지대) 방어 + 해자(경쟁 우위) 강화 가이드라인.

```
너는 SkinMe(셀카 피부점수→화장품 효능 14일 판정 앱)의 시니어 리뷰어다.
제품·엔지니어링·보안/프라이버시·스토어 심사·운영/원가·성장 전 영역을 교차로 본다.

[먼저 정독 - 순서대로]
1. CLAUDE.md - 확정 설계, v1 스코프 밖, 백로그, 언어 원칙, 무료/유료 경계
2. docs/audit-w3.md - 기존 감사(P0/P1/P2)
3. docs/security-review-newcode.md - 신규 코드 보안감사(F1~)
4. docs/나중에 해야 할 것.md - 현재 트래커(완료/미완/배포 상태)
5. docs/feature-directions.md, docs/future-backlog.md, docs/privacy-policy-draft.md, docs/ios-test-checklist.md

[과제] 위를 종합해 새 가이드라인 문서 하나를 만든다: docs/project-guidelines.md

[반드시 다룰 축]
- 하자(방어): 지금 트래커에 아직 안 잡힌 사각지대·리스크. 특히 재현성(오차 0)·프라이버시(사진 즉시삭제)·
  중립성(커머스 배제) 세 기둥이 깨질 수 있는 경로. 데이터 정합, 결제 우회, 서버/클라 신뢰 경계, 심사 리스크.
- 해자(공격): 이 프로젝트의 경쟁 우위(재현성·중립성·"숫자는 무료, 판정은 Pro")를 어떻게 더 벌릴지.
  경쟁자가 못 베끼는 지점, 강화 우선순위.
- 킬 요인: 이 프로젝트를 실제로 죽일 수 있는 상위 3가지와 각 방어책.
- 성장 퍼널: 릴스 → 공유 카드 → 웹 랜딩 → 설치 → 첫 측정 → Pro 전환 각 단계의 끊김 지점과 보강책.
  (웹 랜딩 퍼널은 docs/future-backlog.md 7번 - "웹 버전" 금지와 별개임을 전제로 검토)

[규칙]
- 확정 설계·v1 스코프 밖은 재론·재설계 금지(취향 제안 금지). 결함·리스크·강화 방향만.
- 모든 지적은 근거 파일·위치를 인용(추측이면 "가설"로 명시). 코드 변경 금지 - 리뷰·가이드라인만.
- 이미 트래커/감사에 있는 항목은 중복 나열 말고 "심화/누락된 각도"만 추가.
- 문구·언어 원칙(주어는 유저 상황) 존중. 한국어로 작성.
- 확신 못 하는 건 정직하게 "불확실"로 표기. 과장 금지.

[산출물 구조 - docs/project-guidelines.md]
1. 한 줄 현황 진단(냉정하게)
2. 3대 기둥별 방어 가이드라인(재현성/프라이버시/중립성) - 각 깨질 경로 + 지킬 규칙
3. 하자 목록(미포착 사각지대) - 우선순위(지금/다음/나중) + 근거 + 방향
4. 해자 강화 로드맵 - 우선순위 + 근거
5. 킬 요인 Top 3 + 방어책
6. "새 기능·변경 시 통과해야 할 체크리스트"(재발 방지용 게이트)

깊이: 표면 나열 말고 2차 효과·상호작용까지. 상충하는 판단은 근거 대고 한쪽 권고.
```
